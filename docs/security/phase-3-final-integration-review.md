## Findings and corrections

| ID | Severity / exposure | Finding and disposition |
| --- | --- | --- |
| P3-01 | High impact at the trusted service boundary; no HTTP exploit demonstrated | **Fixed.** Services authorized the company/site attributes of a supplied `AuthorizationScope` but selected records using its independently mutable in-memory ID. A local authorized scope carrying a foreign scope ID could update foreign master data, change foreign numbering configuration or issue a foreign number. All three mutation/allocation services now resolve `AuthorizationScope::context()` inside their transaction before authorization and target lookup. The SQLite writer-lock operation remains before reads. Three regressions reproduced the bypass before the fix and now reject foreign targets with 404 without writes. Existing HTTP requests already constructed canonical contexts and prohibited submitted `scope_id`. |
| P3-02 | Medium, conditional persistence/audit integrity | **Fixed.** `ManageDocumentMasterData` ignored a cancelled model save and a cancelled audit insert. Eloquent listeners returning `false` could leave unaudited changes, or change type/register applicability after cancelling the type update. The service now throws on either cancellation, rolling back the master row, applicability changes and audit together. Three regressions failed before the correction and pass afterward. No browser-controlled event listener was identified. |
| P3-03 | Medium, inherited rollout limitation | **Open, unchanged Phase 2 boundary.** Access-attempt audits share the caller transaction; rollback removes them. Fresh policy queries also do not cancel an in-flight decision or guarantee fresh visibility inside a long MySQL repeatable-read snapshot. Preserve the independent-audit-sink and delivery integration requirements in the Phase 2 review. No new logging infrastructure or authorization semantics were added. |
| P3-04 | Verification gap, required before deployment | **Open.** No approved isolated MySQL environment was found. Trigger behavior, deployment isolation and concurrent registration/configuration mutation have not been executed on MySQL 8.4. SQLite success is not MySQL validation. |

No additional HTTP RBAC, cross-company/site, confidentiality or counter-edit bypass was found in the reviewed Phase 3 surface. This is a source and automated-test review, not production penetration testing or proof of all future workflow behavior.

## Registration transaction contract for Phases 4–6

Reuse [`DocumentNumbering::register()`](../../app/Authorization/DocumentNumbering.php) and [`FormalNumberedRegistration`](../../app/Authorization/FormalNumberedRegistration.php). There is no standalone allocator or HTTP issuance endpoint.

1. Draft creation must not call `register()` and must leave generated number fields unset. Existing configuration/preview operations allocate nothing; a callback returning a draft is rejected and rolled back. Actual draft endpoints do not exist yet.
2. On the formal transition, the workflow owns a short `DB::transaction(..., 1)` on the numbering connection. Derive company/site/register/series/type from authoritative server-loaded data. Enforce the workflow's registration permission, exact organizational/department scope, state transition and idempotency; the currently planned `documents.register` catalog key is unavailable and must not be treated as an existing grant.
3. Call `register($actor, $scope, $seriesId, $persistRegistration)` within that transaction. The service canonicalizes scope, checks `numbering.issue`, locks the register then series/current configuration on MySQL, verifies availability, advances the counter atomically and passes a provisional string to the trusted callback. SQLite takes its writer lock before policy/configuration reads because it ignores `FOR UPDATE`.
4. Inside the callback, enforce current type/register applicability and document-specific policy before persistence. Persist the formal record and required security/profile linkage on the **same connection**. Return a persisted Eloquent model implementing all four interface methods: `numberingScopeId()`, `numberingRegisterId()`, `isFormallyRegistered()` and `registeredNumber(NumberingPurpose)`. The service reloads with a locking read and checks exact scope/register, formal state and stored number. Keys must remain stable and unique within their fixed register family and be at most 128 characters.
5. The nested service transaction/savepoint covers counter advancement, callback writes and the immutable issuance ledger. Exceptions, incorrect callback results, duplicate issuance and failed/cancelled issuance history persistence roll back together, including when caught by the outer caller. Outer rollback also removes successful provisional allocations. Discard returned models/numbers after any rollback.
6. Registration success is the **outer commit**, not the service return. Add restrictive document/master/issuance foreign keys, protect persisted number fields from later editing, and preserve historical type/register associations or a suitable snapshot. These protections belong to the future module; the test fixture is not a production document model. Committed issuance remains in history after business cancellation.
7. Callbacks must not commit/roll back transactions, perform DDL, switch connections or publish/send/write external effects. Publish only after the outer commit under a reviewed idempotent delivery protocol. Commit-acknowledgement loss and business cancellation do not promise legally gapless numbering. The allocator does not retry callbacks. Any later whole-transaction retry needs explicit workflow idempotency and side-effect controls.
8. For a document needing both Outgoing purposes, keep both calls and persistence in one outer transaction and use consistent register/series/document lock ordering. A failure in either must escape or explicitly abort the entire formal transition; catching a failed second call and committing the first would commit a partial business operation. Do not lock a document before the allocator's register lock in another competing path without reviewing the resulting lock dependency.

The SQLite concurrency fixture starts four synchronized PHP workers on separate connections: three committed registrations have distinct sequences 1–3 and matching records/ledger/counter; the deliberate fourth rollback leaves no number consumed. This validates that tested service scenario, not crash durability, MySQL locking or unimplemented workflow retries.

Authorization runs inside the registration boundary, but membership/RBAC reads are not serialized against every concurrent revocation. Avoid long-lived read snapshots; review deployment isolation and lock-wait revocation behavior on MySQL. Do not describe a transaction as making Phase 2 authorization linearizable.

## Security boundaries preserved

- Routes retain `web`, `auth:web` and `EnsureActiveUserSession`; mutations retain CSRF. Form Requests authorize before scoped target lookup, validate relationships/uniqueness and prohibit server-controlled identity, audit and counter fields. Unauthorized hidden/missing targets remain indistinguishable. There is no counter editor, issued-number mutation API, master deletion API, or new delivery route.
- `AccessControl`, `MembershipAccess`, `PermissionCatalog` and current-version sessions remain authoritative. Administration visibility is UI behavior only. The service fixes do not grant permissions or change the Phase 2 central-administration exception.
- `DocumentAccess` with `DocumentSecurityDescriptor` still governs exact metadata/preview/download operations; confidentiality, clearance and per-operation allowlists are unchanged. Master/numbering access never substitutes for document authorization. Generic signed local-storage transport remains disabled. Future record-to-security-profile binding must be atomic and authoritative.
- Master mutations and `MasterDataAudit` share a transaction with server-selected actor, scope and before/after snapshots. Numbering configuration versions and issued ledger rows are transactional mutation audits. Rejected ordinary configuration operations do not universally emit mutation audits. These records are not a durable independent access-attempt sink.
- Numbering configuration/issuance model guards and SQL UPDATE/DELETE/replacement guards preserve history; ownership foreign keys and monotonic counter triggers reject the tested unsafe operations. SQL values are parameter bound; dynamic migration identifiers/guard expressions are fixed source, not request input. Raw writes bypass application RBAC and actor selection, and schema operators can remove guards. Existing model-only protections on RBAC/membership audits remain the low-severity Phase 2 limitation; no new claim of database-wide tamper resistance is made.

## Database portability and outstanding MySQL work

Source review found matching foreign-ID types, explicit composite parent unique keys, restrictive foreign keys, bounded generated strings, portable JSON snapshots and driver-specific trigger definitions. MySQL must use InnoDB with foreign-key checks enabled; `config/database.php` leaves engine selection to the server. SQLite must retain foreign-key enforcement and a suitable busy timeout. The development database was only inspected read-only and still lacks Phase 3 migrations; this review did not migrate it.

No approved disposable MySQL setup or repository MySQL harness was found. No MySQL connection was attempted, and no infrastructure was installed, initialized or configured. Earlier Phase 2 MySQL evidence does not cover Phase 3.

Before deployment, on an explicitly approved disposable MySQL 8.4 database:

- Run fresh and Phase 2-to-3 upgrade migrations; verify schema/index/constraint definitions, trigger installation/definer privileges, rollback and reapplication. MySQL DDL can implicitly commit; create test fixture tables outside transactional test setup. The existing concurrency test/worker is explicitly SQLite-only and must be adapted before it supplies MySQL evidence.
- Exercise INSERT/UPDATE/DELETE, REPLACE and conflict-handling behavior against configuration/issuance history, prefix reservations and counter guards, plus composite foreign keys and maximum sequence bounds. Verify strict SQL mode, utf8mb4/Lao, lengths and case/trailing-space collation differences. Keep migration/trigger privileges separate from runtime credentials. [MySQL trigger requirements](https://dev.mysql.com/doc/refman/8.4/en/create-trigger.html).
- Run synchronized separate-connection allocations for first counter creation, same annual period, rollover and continuous series; include a rollback worker, caught inner failure, outer rollback, duplicate formal-record issuance and ledger-write failure. Assert committed document/ledger/counter consistency, not merely distinct returned strings.
- Interleave issuance with configuration changes and register deactivation; test simultaneous internal/official calls, shared prefix claims and same-record registration. Check register-before-series ordering, foreign-key/next-key locks, deadlocks and lock timeouts. A locking read protects counter allocation differently from an ordinary snapshot read; validate the actual deployment isolation. [MySQL locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).
- Interleave membership/role/user/site revocations with authorization and lock waits. Inference from source and the MySQL manual: ordinary authorization/type-availability reads can retain an older snapshot under repeatable read even while numbering's locking reads see current rows. Record the accepted revocation boundary or review stronger controls before claiming immediate concurrent revocation. [MySQL consistent reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html).

SQLite has one writer; acquiring a writer lock after an established deferred read snapshot can still fail with `SQLITE_BUSY`. Let errors abort the formal transition; do not retry only an allocation or reuse a provisional number. This remains a caller transaction constraint, not an instruction to change infrastructure.
