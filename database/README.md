# Organization foundation — Phase 2.2A

## Structure and integrity

- Companies have a globally unique `code`.
- Sites belong to a company; `(company_id, code)` is unique.
- Departments belong to a site and its company; `(site_id, code)` is unique.
- The department foreign key `(site_id, company_id)` references the explicit unique key `(id, company_id)` on sites. This prevents inconsistent ownership during inserts, updates, bulk writes and site reassignment, even when Eloquent events are bypassed.
- Company foreign keys and the department/site composite foreign key restrict deletion and updates of referenced keys. There are no cascaded deletions.
- `Department` validates the company/site pair on normal Eloquent saves. Database constraints remain authoritative for concurrent changes and bulk writes.
- English and Lao names are required strings; `active` defaults to true and is cast to a boolean by Eloquent.

Deactivate historical master records with `active = false`. The explicit `active()` scopes filter only the record's own flag. Ordinary queries and relationships retain inactive records. Parent deactivation does not change child flags or remove history. These flags and scopes are not authorization or site-access enforcement.

No organization mutation endpoints or management screens are supplied in this phase. Phase 2.2C adds scoped role/permission administration, but organization maintenance remains unavailable; see the main README. Future document and user references must add their own restrictive foreign keys.

## Controlled XPPL initialization

After reviewing and applying the migrations, run the explicit command below with verified English and Lao names. Replace the placeholders; they are not official master data.

```sh
php artisan organization:initialize-xppl \
    --company-name-en='VERIFIED ENGLISH COMPANY NAME' \
    --company-name-lo='VERIFIED LAO COMPANY NAME' \
    --site-name-en='VERIFIED ENGLISH SITE NAME' \
    --site-name-lo='VERIFIED LAO SITE NAME' \
    --no-interaction
```

All four names are required and limited to 255 characters. Only company code `XPPL` and site code `XPPL` within that company are initialized. IDs are generated by the database and resolved through relationships. Initialization is transactional and repeatable; existing names, IDs, timestamps and active flags are preserved. It can also complete an existing XPPL company that has no XPPL site.

The command is not called by migrations or the default seeder. The default seeder intentionally does nothing. No users, passwords, administrator accounts, roles, departments, HQ or KSO records are initialized. Factories contain fictional test data only. Department master data must await verification.

## SQLite / MySQL 8.4 considerations

- The same migrations define required columns, scoped unique keys, restrictive foreign keys and the company/site composite constraint for both databases. No database-specific triggers or check constraints are needed.
- SQLite foreign-key enforcement must remain enabled (`DB_FOREIGN_KEYS=true`, the existing default). With it disabled, direct SQL can bypass ownership and deletion restrictions.
- MySQL must use InnoDB with foreign-key checks enabled. The explicit unique parent key `(id, company_id)` avoids reliance on non-standard references to non-unique keys, which MySQL 8.4 restricts. IDs and foreign IDs use Laravel's matching unsigned big integer types on MySQL.
- MySQL's existing configuration uses `utf8mb4`, which supports Lao; SQLite stores Unicode strings natively.
- Code comparisons follow the configured database collation. SQLite's default comparison is case-sensitive; the configured MySQL `utf8mb4_unicode_ci` comparison is case-insensitive and may ignore accents or trailing spaces. Use consistent uppercase organizational codes. Direct writes with case/spacing variants may therefore be accepted by SQLite and rejected by MySQL. This phase does not silently rewrite codes.
- SQLite ignores declared VARCHAR lengths and uses dynamic typing; MySQL in strict mode enforces VARCHAR lengths and typed integer storage for Laravel's boolean columns. Neither migration adds a CHECK limiting `active` to only 0/1. Initialization validates name lengths before writing; future input boundaries must validate code length (32), name length (255) and boolean values. The required ownership and uniqueness constraints are enforced by both databases.
- MySQL DDL is not transactional in the same way as SQLite DDL. Migrations are separate, ordered creates (companies, sites, departments); rollbacks drop them in reverse order. Rolling back populated tables destroys their records and is not a substitute for deactivation.

Automated persistence/integrity tests use the isolated in-memory SQLite database configured in `phpunit.xml`. Phase 2.2C also ran the complete PHP suite, including these organizational integrity regressions, against a disposable MySQL 8.4.11 instance with repository-local data and networking disabled. No existing company database was used. See the main README for the RBAC constraints and verification boundaries. Do not point migration or test commands at LVC Inventory or XPPL Toll databases.

Database references: [MySQL 8.4 foreign-key requirements](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html), [SQLite foreign-key enforcement](https://www.sqlite.org/foreignkeys.html), and [SQLite types and collations](https://www.sqlite.org/datatype3.html).

## Phase 3A document master data

`document_categories`, `document_types` and `register_configurations` belong to an exact persisted company or site authorization scope. Company and site definitions are independent; there is no automatic inheritance of reference rows. Codes are uppercase stable identifiers unique within their scope. English/Lao names and optional descriptions are editable. Type category ownership, codes, register identity and scope are immutable through application writes. Deactivate records instead of deleting them; no deletion API exists. Composite foreign keys keep a type, its category and its applicable register configurations in the same scope, with restrictive deletes/updates.

Registers reuse the existing `DocumentResourceType` identities: `incoming`, `outgoing`, `controlled`. Their bilingual names are application labels; each scope can configure at most one row for each identity. Types must have at least one applicable register. Creating or activating a type requires active parents. Parent deactivation immediately makes the corresponding applicability ineffective without rewriting historical configuration. `DocumentType::effectiveFor()` reloads current configuration; it checks reference availability only, never document authorization.

`master-data.view` and `master-data.manage` are controlled operational catalog keys. Requests require an active, current-version authenticated session, the appropriate scoped role permission and exact company/site membership. Department-only membership cannot administer a whole site's master data. The central identity-administration exception does not apply. No existing role automatically receives these keys; the existing repeatable `rbac:initialize` procedure can add catalog definitions without assigning users or overwriting configured role grants. Initial operational role provisioning remains a separately reviewed operator/integration action. This phase executes no initializer or migration against the development database and provides no operational seed records.

Administration uses the authenticated `/api/v1/document-master-data/{categories|types|registers}` GET/POST and PATCH `/{record}` endpoints. Target lookup happens after authorization inside the exact scope; hidden and missing records both return 404. Relationship and uniqueness validation are scoped. `/api/v1/document-master-data/classifications` is GET-only and derives its fixed reference values from the existing `Confidentiality` enum; it creates no additional confidentiality model, clearance or entitlement.

Supported management mutations and `master_data_audits` inserts share a transaction, recording the server-selected actor, scope, subject, action and before/after configuration. Audit failure rolls back the mutation. Model guards and SQLite/MySQL UPDATE/DELETE triggers protect audit history. These are transactional configuration-change audits, not an independent access-attempt sink; caller rollback removes both state and audit, consistent with the Phase 2 security review. Privileged direct SQL remains outside application identity/authorization/audit enforcement.

Future persisted registration must use stable master IDs, enforce current type/register availability, constrain document references with restrictive foreign keys, and authorize the document operation through `DocumentAccess` immediately before protected responses. In particular, adding references to type/register applicability must prevent removal of a referenced association or retain an explicit historical snapshot. Master-data management is not a document-content permission. There are no counters, number allocation/formatting, document lifecycle or file-delivery operations here.

Phase 3A verification uses the isolated SQLite suite and frontend tests. The schema uses matching foreign-ID types, explicit composite unique parent keys, fixed register enums and portable JSON audit snapshots for MySQL 8.4 compatibility. MySQL was not rerun for this phase: no existing isolated test instance was available, and the earlier disposable instance documented above was removed. Do not point these tests or migrations at operational databases.
