# Organization foundation — Phase 2.2A

Current authorization follows the [System Administrator contract](../README.md#current-system-administrator-authority): an active global `SECURITY_ADMINISTRATOR` assignment has full system and audited document access. Exact memberships and separate operational grants described in the phase history below still apply to ordinary users and scoped administrators. This requires no account, grant or data migration.

## Structure and integrity

- Companies have a globally unique `code`.
- Sites belong to a company; `(company_id, code)` is unique.
- Departments belong to a site and its company; `(site_id, code)` is unique.
- The department foreign key `(site_id, company_id)` references the explicit unique key `(id, company_id)` on sites. This prevents inconsistent ownership during inserts, updates, bulk writes and site reassignment, even when Eloquent events are bypassed.
- Company foreign keys and the department/site composite foreign key restrict deletion and updates of referenced keys. There are no cascaded deletions.
- `Department` validates the company/site pair on normal Eloquent saves. Database constraints remain authoritative for concurrent changes and bulk writes.
- English and Lao names are required strings; `active` defaults to true and is cast to a boolean by Eloquent.

Deactivate historical master records with `active = false`. The explicit `active()` scopes filter only the record's own flag. Ordinary queries and relationships retain inactive records. Parent deactivation does not change child flags or remove history. These flags and scopes are not authorization or site-access enforcement.

No organization mutation endpoints or management screens are supplied in this phase. Phase 2.2C adds scoped role/permission administration, but organization maintenance remains unavailable; see the main README. Future document and user references must add their own restrictive foreign keys.

## Controlled XPPL initialization

After reviewing and applying the migrations, run the explicit command below with verified English and Lao names. Replace the placeholders; they are not official master data.

```sh
php artisan organization:initialize-xppl \
    --company-name-en='VERIFIED ENGLISH COMPANY NAME' \
    --company-name-lo='VERIFIED LAO COMPANY NAME' \
    --site-name-en='VERIFIED ENGLISH SITE NAME' \
    --site-name-lo='VERIFIED LAO SITE NAME' \
    --no-interaction
```

All four names are required and limited to 255 characters. Only company code `XPPL` and site code `XPPL` within that company are initialized. IDs are generated by the database and resolved through relationships. Initialization is transactional and repeatable; existing names, IDs, timestamps and active flags are preserved. It can also complete an existing XPPL company that has no XPPL site.

The command is not called by migrations or the default seeder. The default seeder intentionally does nothing. No users, passwords, administrator accounts, roles, departments, HQ or KSO records are initialized. Factories contain fictional test data only. Department master data must await verification.

## SQLite / MySQL 8.4 considerations

Current local MySQL evidence and reproduction instructions are in the [isolated MySQL 8.4 verification report](../docs/security/mysql-8-4-verification.md). This follow-up uses Docker Engine and MySQL 8.4.13 Community, without changing the default SQLite configuration. Earlier phase-specific verification statements below describe their original review dates.

- The same migrations define required columns, scoped unique keys, restrictive foreign keys and the company/site composite constraint for both databases. No database-specific triggers or check constraints are needed.
- SQLite foreign-key enforcement must remain enabled (`DB_FOREIGN_KEYS=true`, the existing default). With it disabled, direct SQL can bypass ownership and deletion restrictions.
- MySQL must use InnoDB with foreign-key checks enabled. The explicit unique parent key `(id, company_id)` avoids reliance on non-standard references to non-unique keys, which MySQL 8.4 restricts. IDs and foreign IDs use Laravel's matching unsigned big integer types on MySQL.
- MySQL's existing configuration uses `utf8mb4`, which supports Lao; SQLite stores Unicode strings natively.
- Code comparisons follow the configured database collation. SQLite's default comparison is case-sensitive; the configured MySQL `utf8mb4_unicode_ci` comparison is case-insensitive and may ignore accents or trailing spaces. Use consistent uppercase organizational codes. Direct writes with case/spacing variants may therefore be accepted by SQLite and rejected by MySQL. This phase does not silently rewrite codes.
- SQLite ignores declared VARCHAR lengths and uses dynamic typing; MySQL in strict mode enforces VARCHAR lengths and typed integer storage for Laravel's boolean columns. Neither migration adds a CHECK limiting `active` to only 0/1. Initialization validates name lengths before writing; future input boundaries must validate code length (32), name length (255) and boolean values. The required ownership and uniqueness constraints are enforced by both databases.
- MySQL DDL is not transactional in the same way as SQLite DDL. Migrations are separate, ordered creates (companies, sites, departments); rollbacks drop them in reverse order. Rolling back populated tables destroys their records and is not a substitute for deactivation.

Automated persistence/integrity tests use the isolated in-memory SQLite database configured in `phpunit.xml`. Phase 2.2C also ran the complete PHP suite, including these organizational integrity regressions, against a disposable MySQL 8.4.11 instance with repository-local data and networking disabled. No existing company database was used. See the main README for the RBAC constraints and verification boundaries. Do not point migration or test commands at LVC Inventory or XPPL Toll databases.

Database references: [MySQL 8.4 foreign-key requirements](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html), [SQLite foreign-key enforcement](https://www.sqlite.org/foreignkeys.html), and [SQLite types and collations](https://www.sqlite.org/datatype3.html).

## Phase 3A document master data

`document_categories`, `document_types` and `register_configurations` belong to an exact persisted company or site authorization scope. Company and site definitions are independent; there is no automatic inheritance of reference rows. Codes are uppercase stable identifiers unique within their scope. English/Lao names and optional descriptions are editable. Type category ownership, codes, register identity and scope are immutable through application writes. Deactivate records instead of deleting them; no deletion API exists. Composite foreign keys keep a type, its category and its applicable register configurations in the same scope, with restrictive deletes/updates.

Registers reuse the existing `DocumentResourceType` identities: `incoming`, `outgoing`, `controlled`. Their bilingual names are application labels; each scope can configure at most one row for each identity. Types must have at least one applicable register. Creating or activating a type requires active parents. Parent deactivation immediately makes the corresponding applicability ineffective without rewriting historical configuration. `DocumentType::effectiveFor()` reloads current configuration; it checks reference availability only, never document authorization.

`master-data.view` and `master-data.manage` are controlled operational catalog keys. Requests require an active, current-version authenticated session, the appropriate scoped role permission and exact company/site membership. Department-only membership cannot administer a whole site's master data. The central identity-administration exception does not apply. No existing role automatically receives these keys; the existing repeatable `rbac:initialize` procedure can add catalog definitions without assigning users or overwriting configured role grants. Initial operational role provisioning remains a separately reviewed operator/integration action. This phase executes no initializer or migration against the development database and provides no operational seed records.

Administration uses the authenticated `/api/v1/document-master-data/{categories|types|registers}` GET/POST and PATCH `/{record}` endpoints. Target lookup happens after authorization inside the exact scope; hidden and missing records both return 404. Relationship and uniqueness validation are scoped. `/api/v1/document-master-data/classifications` is GET-only and derives its fixed reference values from the existing `Confidentiality` enum; it creates no additional confidentiality model, clearance or entitlement.

Supported management mutations and `master_data_audits` inserts share a transaction, recording the server-selected actor, scope, subject, action and before/after configuration. Audit failure rolls back the mutation. Model guards and SQLite/MySQL UPDATE/DELETE triggers protect audit history. These are transactional configuration-change audits, not an independent access-attempt sink; caller rollback removes both state and audit, consistent with the Phase 2 security review. Privileged direct SQL remains outside application identity/authorization/audit enforcement.

Future persisted registration must use stable master IDs, enforce current type/register availability, constrain document references with restrictive foreign keys, and authorize the document operation through `DocumentAccess` immediately before protected responses. In particular, adding references to type/register applicability must prevent removal of a referenced association or retain an explicit historical snapshot. Master-data management is not a document-content permission. There are no counters, number allocation/formatting, document lifecycle or file-delivery operations here.

Phase 3A verification uses the isolated SQLite suite and frontend tests. The schema uses matching foreign-ID types, explicit composite unique parent keys, fixed register enums and portable JSON audit snapshots for MySQL 8.4 compatibility. MySQL was not rerun for this phase: no existing isolated test instance was available, and the earlier disposable instance documented above was removed. Do not point these tests or migrations at operational databases.

## Phase 3B secure document numbering

The [Phase 3 final integration review](../docs/security/phase-3-final-integration-review.md) records the final security corrections, registration contract for Phases 4–6, verification evidence and Phase 4A checklist. The subsequent [isolated MySQL verification](../docs/security/mysql-8-4-verification.md) records executed Phase 2/3 migrations, constraints and concurrent numbering checks, plus remaining deployment limitations.

### Series, purposes and formats

`numbering_series` has one permanent row per scoped register configuration and purpose, enforced by a unique key. Company and site configurations stay independent. A series cannot change its scope, register, purpose or reset policy, even while inactive. There is therefore no second overlapping series for the same purpose or year. Reconfigure/reactivate the existing series instead of replacing it. The purposes are `internal_register` and `official_outgoing`; the latter is restricted to the Outgoing register. External references remain ordinary externally supplied registration data, outside this service and without an invented global uniqueness constraint.

Formats are deliberately limited to `PREFIX/YEAR/SEQUENCE`. Prefixes use bounded uppercase ASCII segments; padding is a minimum width of 1–12 digits, not a truncation rule. The maximum sequence is 999,999,999,999. The year component is mandatory, including for continuous sequences. Annual counters use their Gregorian issuance year as the period; continuous counters use period `0`. Issuance obtains the year from the server application timezone, currently UTC; confirm the operational timezone before rollout. Preview accepts an example year and always renders sequence 1 without reading, reserving or advancing counters.

`numbering_namespaces` reserves every prefix globally and permanently to one series, including old prefixes and inactive configurations. Managers should include the necessary company/site/register/purpose distinction in their prefixes. This intentionally prevents different organizations or purposes from generating the same complete identifier; it does not apply to external references. A generic conflict response does not disclose the owner of a reserved prefix. The fixed two suffix segments make prefixes unambiguous. A prefix change or padding edit does not create a new counter, reset an existing period or rewrite any issued string.

### Effective configuration history and Administration

`numbering_configurations` is append-only configuration history: version, prefix, padding, active flag, change reason, server-selected actor and effective timestamp. Edits take effect immediately, serialized against issuance; the highest version is the single current configuration. No future scheduling or arbitrary overlapping date intervals are supported. Version order resolves changes sharing a timestamp. Existing issued numbers retain their exact configuration ID and rendered value. Identical configuration saves are non-consuming no-ops.

Administration offers scoped listing, creation, format preview, editing/activation, and paginated history in English/Lao. Register, purpose and reset-policy controls become read-only after creation. There is no counter editor, issuance endpoint, draft allocator or issued-number mutation API. `numbering.view` authorizes configuration/history/preview; `numbering.manage` authorizes configuration changes; `numbering.issue` is a separate service-only operational capability. Each requires the matching effective company/site membership and active scoped RBAC grants. Central identity administration receives no exception or default numbering grant. Numbering permissions supply neither document reading rights nor clearance. Catalog initialization adds definitions only; no initializer, real series, counter, account or role grant was executed by this phase.

### Formal-registration service contract

Call `DocumentNumbering::register($actor, $scope, $seriesId, $persistRegistration)` **inside a caller-owned database transaction** during the formal registration transition. It is not a draft creation helper. There is no public standalone allocation method. The callback receives a provisional rendered string and must persist the formal record on the same Laravel database connection. It must return a persisted Eloquent model implementing `FormalNumberedRegistration`. The service reloads it and verifies formal state, exact scope/register and the stored number for that purpose. Unsaved models, incorrect ownership/state/number or another connection fail closed.

The callback is trusted module code, not request input. It must not commit/roll back the transaction, perform DDL, switch connections, perform network/file/publication side effects or hand provisional numbers to external systems. The service uses a nested transaction/savepoint with one attempt: counter advancement, callback persistence and immutable issuance history all roll back together on any error, even if an outer caller catches it. An outer rollback also removes them. Return to the caller is not a commit acknowledgement; discard provisional numbers and stale model instances after rollback. External publication belongs after the outer commit, with its own reviewed delivery/idempotency protocol. Do not automatically retry a callback with side effects.

`issued_document_numbers` is the committed issuance ledger, separate from mutable counter state. It stores series/configuration, period/year/sequence, rendered number, actor and a bounded persisted record key within the fixed register family. PHP class names are not used as issuance identity, so a class rename cannot silently bypass duplicate-registration protection. Future modules must keep keys stable and unique within that register family. Unique keys protect the complete generated identifier, series/period/sequence and series/formal-record identity. Reissuing the same purpose to the same record rolls back, rather than changing its number or consuming another sequence. A formal Outgoing record may have one internal number and a separately issued official number. Future modules must protect persisted identifier fields and add restrictive document/issuance references within the same outer transaction; they must also implement workflow permission/resource-policy checks, formal-transition/idempotency guards and record retention. The interface is not a substitute for those future document policies or a way to prove business state independently of trusted module code.

### Atomic allocation and database differences

MySQL takes the scoped register lock first, then the permanent series lock, then locks its current configuration/counter. This register-before-series order also coordinates internal and official issuance in the same outer transaction, avoiding a reversed lock dependency between those purposes. The persisted formal record is reloaded with a locking read before validating its stored number and ownership. Counter creation has a unique `(series_id, period)` key; advancement is a guarded SQL `value = value + 1` update, followed by a locked read. The lock serializes counter creation, allocation and configuration changes for that series. Unique issued-number constraints remain the final duplicate barrier. No sequence is calculated by an unprotected application read/increment.

SQLite ignores `FOR UPDATE`. The numbering paths first perform a no-op write to the exact series row to acquire SQLite's writer lock before their policy/configuration/counter reads. SQLite has one writer at a time; its native transaction/savepoint rollback retains atomicity. The configured SQLite busy timeout defaults to 5,000 ms (`DB_BUSY_TIMEOUT`). A caller that has already established a deferred read snapshot may still get `SQLITE_BUSY` when upgrading. Use a short registration transaction and acquire numbering's write boundary before unrelated reads, or an explicitly reviewed immediate transaction on the caller's connection. Busy/deadlock/timeout errors abort; this service never retries the registration callback. Any later whole-transaction retry needs module-level idempotency and must not repeat external side effects.

The schema has composite ownership/configuration/counter foreign keys, scoped purpose uniqueness, enum checks, prefix/format guards and monotonic counter guards. Configuration and issuance rows reject model updates/deletes and database UPDATE/DELETE/replacement attempts. Counters cannot be rewound, skipped or deleted through normal SQL operations guarded by these triggers; new periods start at zero. Runtime credentials must not have unrestricted schema/trigger privileges. Database operators capable of removing guards remain outside application enforcement.

Configuration versions and issuance ledger rows are transactional mutation audits. Persistence failure or cancelled history inserts fail closed. Rollback removes history with the corresponding operation; these are not transaction-independent access-attempt logs. The Phase 2 durable-audit-sink limitation remains unchanged. Records contain configuration/opaque identifiers, never document contents, passwords, credentials or attachments. Committed issuance remains recorded after later business cancellation. This supports ordinary operational numbering, not a promise of legally gapless numbers after cancellation, disaster recovery, commit-acknowledgement loss or external publication failures.
